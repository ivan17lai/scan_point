ARCHITECTURE · DATA · FILE LAYOUT

ScanPoint 是怎麼組起來的

這份文件寫給要維護、除錯或改寫 ScanPoint 的人。它描述三個模組怎麼分工、 一次刷卡從讀卡機到名次之間經過哪些地方、每個檔案放在哪裡又存了什麼， 以及成績實際上是照什麼規則算出來的。

離線優先 站點不需要網路就能完整記錄，雲端只是選用的匯總層
三份副本 每一筆刷卡同時寫進主檔、常駐存檔與（選用的）隨身碟
純文字 沒有資料庫。JSONL 逐行附加，斷電最多只損失最後一行

01

三個模組

專案分成三個資料夾，彼此只透過檔案與一個 HTTP 端點往來， 沒有共用的執行期狀態。任何一個模組停擺，其他兩個仍然能各自運作。

模組職責
資料夾是什麼負責
scanpoint/ Flutter 桌面應用程式（Windows kiosk） 解碼讀卡機訊框、判定重複、寫入三份紀錄、匯出與上傳
web/ 零建置靜態網站，由 GitHub Pages 發佈 部署教學與金鑰產生、成績計算頁、Apps Script 原始碼
score_center/ 保留位置 目前計分規則實作在 web/score-engine.js
為什麼站點之間不互相通訊

檢查點通常在收訊不穩的地方，而且經常無人看管。任何「站點必須連得上某個東西才能記錄」 的設計，都會把一次網路中斷變成一整段時間的成績遺失。所以站點只對本機磁碟負責， 匯總是事後的、可以重試的動作。

02

一次刷卡的生命週期

讀卡機被設定成鍵盤模擬（keyboard wedge），刷卡時它就像有人飛快打字一樣送出按鍵。 從那一刻到畫面亮起綠燈，中間經過六個階段。

  1. 訊框組裝

    讀卡機送出 ;<卡號>?。ScanDecoder 依實體按鍵位置判讀， 而不是系統認為被打出來的字元——; 是分號鍵未按 Shift，? 是斜線鍵加 Shift。 這就是為什麼注音輸入法、非美式鍵盤配置與 CapsLock 都不會弄壞它。

  2. 時間護欄

    兩個按鍵之間超過 300ms 判定中斷（E-01）， 從 ; 到 ? 超過 1500ms 判定逾時（E-02）。 刷卡機一格約 5–30ms，人手打字不可能通過這道門檻。

  3. 正規化與驗證

    卡號一律轉大寫，並必須符合 ^[A-Za-z0-9\-_.:]{1,64}$， 否則丟出 E-03。原始字串會另外保留在 raw 欄位，供事後診斷設定錯誤的讀卡機。

  4. 重複判定

    以 站點編號|卡號 為鍵查詢本機的首次出現時間。 已經出現過的，仍然會被寫入並標上 duplicate_of， 但不會增加該站的有效計數——「這個人刷了兩次」本身就是值得保留的證據。

  5. 三份寫入

    同一行 JSON 依序附加到主檔、常駐存檔與（若有設定）隨身碟，每份都 flush 到磁碟， 同時各自維護一份當日 CSV。只要有一份成功就算記錄成功： 不能因為某個備份位置壞掉，就把選手趕回去重刷。

  6. 回饋與歸位

    成功／重複／錯誤各有不同提示音與畫面，分別停留 2.5 / 3.0 / 3.5 秒後回到待機。 「掃描中」畫面有 400ms 的最短顯示時間，否則它會一閃而過像是當機。 整個過程另外寫一筆到操作日誌。

兩份日誌，各司其職

scans.jsonl 是結果——會變成某個人成績的那些行，乾淨到可以直接丟進試算表。 events.jsonl 是過程——失敗的讀取、PIN 嘗試、設定變更與時間點。 活動結束後最常被問的問題是「為什麼這個人少一個點」，而回答它需要的是失敗紀錄與設定變更，不只是成功紀錄。

03

檔案系統

站點沒有資料庫。所有東西都是純文字檔，分佈在三個位置—— 一個主要位置與兩個備援位置。

主檔（執行檔旁）

程式啟動時只從這裡讀取紀錄。設定檔也放在這裡。 

scan_point.exe 所在資料夾/
├── scan_point.exe
├── station.json            站點編號、名稱、管理 PIN、額外備份路徑
├── cloud.config            SPREADSHEET_ID / UPLOAD_URL / UPLOAD_KEY
├── id-mapping.json         卡號 → 顯示名稱（選用）
└── data/
    ├── scans.jsonl         刷卡紀錄，逐行附加
    ├── scans-2026-08-10.csv    同樣內容的當日 CSV
    ├── events.jsonl        操作日誌，逐行附加
    └── system_operations.csv   同樣內容的 CSV

常駐存檔（AppData）

由作業系統決定的應用程式支援資料夾底下的 data/，內容與主檔相同。 它只寫不讀：程式永遠不會自動從這裡救回資料。 這是刻意的——自動回填會讓一份舊資料在無人察覺的情況下改變現場狀態， 需要它的時候請手動複製。

額外備份（選用，通常是隨身碟）

在管理面板選一個資料夾就會啟用。它是附加而不是轉移—— 原本的兩份照常寫入，所以拔掉隨身碟不會讓站點比沒插的時候更糟。 

<選定的資料夾>/scan_point/<站點編號>/
├── scans.jsonl
├── scans-2026-08-10.csv
├── events.jsonl
└── system_operations.csv

路徑按站點編號分層，因為一支隨身碟很可能會收集好幾台機器。 少了這一層，第二台插上去就會覆蓋第一台的紀錄，而且是無聲的全毀。 活動中途才插上隨身碟時，程式會把整份既有紀錄複製過去， 所以拿到的是整場活動，不是後半場。

設定檔的讀取來源
檔案從哪裡讀為什麼
station.json 只認執行檔旁邊那一份 放在文件夾或 AppData 的舊副本，絕不能改變一個剛解壓縮出來的新站點的身分
cloud.config 執行檔旁 → 文件夾 OrienteeringSystem/ → AppData，取第一個找到的 雲端金鑰是整場活動共用的，允許放在使用者資料夾集中管理
id-mapping.json 只認執行檔旁邊那一份 只影響畫面顯示，不參與重複判定、匯出、上傳或計分

04

紀錄格式

刷卡紀錄 scans.jsonl

一行一筆，逐行附加。斷電最多只會弄壞最後一行，之前的內容完好。

{"record_id":"scan-3f2a9c1d4e5b6078","seq":42,"card":"04A1B2C3",
 "at_local":"2026-08-10T09:14:05.317","at_utc":"2026-08-10T01:14:05.317Z",
 "station_id":"CP02","station_name":"水源地","term":"questionMark",
 "raw":"04a1b2c3"}
欄位說明
record_id由站點編號、序號、卡號與 UTC 時間推導的穩定識別碼，重複上傳時用來去重
seq該機器的遞增序號
card正規化後的卡號（一律大寫）
at_local / at_utc刷卡時間。計分一律採用 at_utc
station_id / station_name寫入當下的站點身分
term訊框結尾方式：questionMark 或 enterKey
raw正規化前、原封不動的字串
duplicate_of只有重複刷卡才有，值是這張卡在這一站的首次出現時間

當日 CSV scans-YYYY-MM-DD.csv

與 JSONL 同步寫入，方便直接丟進試算表。表頭固定為：

seq,card_id,at_local,at_utc,station_id,station_name,terminator,duplicate_of

操作日誌 events.jsonl

記錄程式做了什麼，而不是選手做了什麼。事件類型是封閉集合， 可以在活動後直接過濾而不用猜字串：

app_startapp_exit scan_okscan_duplicate scan_failadmin_unlock admin_pin_rejectedadmin_exit config_changestorage_change id_mapping_changeexport uploadwrite_error

pin、upload_token、UPLOAD_KEY 這幾個欄位的值會被替換成 <已隱藏>——保留「這個欄位被改過」這件事，但不讓機密隨著隨身碟或共用試算表流出去。 寫入日誌的動作永遠不會拋出例外：因為日記寫不進去而停止記錄刷卡，會是很荒謬的失分方式。

05

雲端試算表結構

雲端這一層完全是選用的。啟用後，Apps Script 會在試算表裡維護四個分頁。 寫入端 doPost 以 UPLOAD_KEY 驗證， 讀取端 doGet?action=scores 以 READ_KEY 驗證，兩者是分開的金鑰。

分頁內容去重依據
scans 所有站點的刷卡紀錄，成績計算頁讀的就是這個分頁 record_id
operations 所有站點的操作日誌 event_id
uploads 每次上傳的收據：送出幾筆、接受幾筆、略過幾筆 不去重，逐筆附加
summary 每個站點一列的統計 依 station_id 就地更新

紀錄分頁的欄位會被設成純文字格式。少了這一步，Google 試算表會重新解讀寫進去的值： ISO 時間戳變成試算表語系的日期，帶前導零的卡號變成數字而不再對得上原本那張卡。 兩種損壞都是無聲的，而且都要等到成績已經算錯了才會浮現。

上傳是可以重按的

伺服器端以 record_id 去重，所以重複送出同一批紀錄不會產生重複列， 只會回報「略過幾筆」。網路不穩時直接再按一次即可。

06

成績計算規則

計分完全在瀏覽器裡完成（web/score-engine.js），資料不會被送到任何地方。 流程固定是這六步：

  1. 去重

    以 record_id 為準；沒有 record_id 的來源退回 卡號 + 站點 + 時間戳 組合。被標記 duplicate_of 的紀錄整筆排除。

  2. 依卡號分組並按時間排序

    同一張卡的所有紀錄依 at_utc 由早到晚排列。

  3. 依站點順序比對

    用一個只能往前走的游標，依設定的站點順序逐一尋找。 找不到就停在那裡——所以判定「有沒有通過」的實際依據是時間戳的先後， 不只是「有沒有刷過」。

  4. 判定完賽

    比對到的站數等於設定站數才算完賽，否則記為 已完成 / 總數。

  5. 計算耗時

    完賽者的成績 = 最後一站時間 − 第一站時間。未完賽者沒有成績。

  6. 排序與名次

    完賽者排在前面，依耗時由小到大；耗時相同則並列同名次， 下一個不同耗時的人接續實際位次。未完賽者排在後面， 依已完成站數多寡、再依起點時間先後排列，且不給名次。

站點順序必須是實際路線

成績頁預設會把資料中出現過的所有站點依編號自然排序填進去，那不一定是活動路線。 如果資料裡混進測試卡或測試站的紀錄，它也會被當成必經站點，導致全員判定未完賽。 按下計算之前請確認站點順序列與實際路線一致。

07

設計取捨

幾個看起來像缺點、但其實是刻意選擇的地方。

為什麼不用資料庫
無人站最實際的故障是沒電或有人拔插頭。逐行 flush 的純文字檔在這種情況下最多退化成 「最後一行可能不完整」，而寫到一半的資料庫頁面可能帶走整個檔案。
為什麼重複刷卡也要寫進去
刪掉它等於刪掉證據。重複紀錄會被標記、不列入計數、計分時排除， 但它留在紀錄裡，讓事後可以回答「這個人到底刷了幾次、什麼時候」。
為什麼常駐存檔不會自動救援
自動回填意味著一份舊資料可以在沒人察覺的情況下改變現場狀態。 備援的價值在於它是一份可以被人檢查後再決定怎麼用的副本，而不是一個會自己作主的機制。
為什麼 ID 對照表只影響顯示
對照表刻意放在紀錄結構之外。改一個顯示名稱不應該有任何機會去改變重複判定、 匯出內容、上傳內容或計分結果。紀錄裡永遠是原始卡號。
為什麼解碼器不碰輸入框
只要沒有任何文字輸入元件取得焦點，輸入法就不會被啟動， 執行中的注音輸入法也就無法攔截、緩衝或改寫讀卡機送出的按鍵。

08

現場注意事項

各站時鐘必須一致

成績是跨站相減出來的，而且完賽判定依賴時間戳的先後。 某一站的時鐘慢了幾分鐘，該站的紀錄會排到前一站前面， 比對就再也找不到它——選手三個點都刷了，卻顯示未完賽。 活動前請逐台校時。

站點編號會進到路徑與計分欄位

它會變成隨身碟上的資料夾名稱，也會被貼回成績頁的站點順序欄位， 而那個欄位以逗號、分號與箭號分隔。建議只用英數字與 - _。

對照表的卡號要對得上

紀錄裡的卡號一律是大寫。對照表若使用小寫十六進位，會對不上而顯示原始 ID。

管理 PIN 預設值是公開的

預設 PIN 寫在開源程式碼裡，本身不保護任何東西。首次設定站點時務必改掉。

同一批資料不要重複載入

成績頁可以同時吃 JSONL 與 CSV。把同一個站的兩種檔案一起拖進去， 掃描筆數統計會翻倍。擇一即可。

折返路線目前不支援

同一個站點在路線中只能出現一次；同一張卡在同一站的第二次刷卡會被視為重複。
